Most custom cursors are the same trick wearing different clothes: a `div`, a `mousemove` listener, and a `transform: translate()`. It works, technically. It's also completely forgettable — the moment your cursor doesn't _react_ to anything, it stops being a feature and starts being a slightly laggy version of the one the OS already gave you for free.

I wanted mine to actually earn its place on the page. Here's what it took.

## Starting point: one div, doing its best

The first version was honest but bland — a single circle following the mouse with a spring, swapping to a blend mode over certain elements. It worked, but it had three real problems:

- **No texture.** One shape, one size, one job.
- **No performance headroom.** It called `document.elementFromPoint()` on _every_ `mousemove` — a layout + hit-test, dozens of times a second, just to check what was under the mouse.
- **No language for hover states.** Buttons, links, and text all felt identical to hover over.

None of that shows up in a screen recording of the finished product, but it's exactly why the finished product needed a rewrite instead of a patch.

## Splitting one cursor into two

The biggest visual upgrade cost nothing extra: a small **dot** riding at the true cursor position, and a larger **ring** trailing it with a softer spring. Two independent `motion` values, one shared paint function per animation frame.

```ts
const RING_SPRING = { type: "spring", stiffness: 260, damping: 26, mass: 0.4 };
const DOT_SPRING = { type: "spring", stiffness: 900, damping: 40, mass: 0.2 };
```

The dot is snappy and precise. The ring lags just enough to read as _intentional_ rather than laggy — that gap between the two is what gives the whole thing weight.

## Killing the perf tax

The original hover-detection ran a geometry query on every mouse pixel moved. The fix was to stop asking "what's under the mouse right now?" and instead let the DOM tell me, via event delegation:

```ts
document.addEventListener("pointerover", (e) => {
  const target = (e.target as Element).closest("[data-cursor]");
  // ...apply variant based on target.dataset.cursor
});
```

No layout thrashing, no polling — the browser already knows what you're hovering, I just had to listen for it instead of asking for it forty times a second.

## Giving hover states a vocabulary

Every interactive element now declares its own cursor behavior right in the markup:

```html
<a href="/work" data-cursor="pointer">Project</a>
<button data-cursor="text" data-cursor-text="View">Case study</button>
<div data-cursor="blend">Dark section</div>
<button data-cursor="pointer" data-cursor-magnetic>Subscribe</button>
```

`pointer` scales the ring up. `text` scales it further and prints a label inside it. `blend` swaps to `mix-blend-mode: lighten` so the cursor stays legible over dark imagery instead of disappearing into it. `magnetic` pulls the whole cursor toward the element's center as you approach, like the button is gently claiming it.

Nothing in the component itself needed to change to add a new hover state to a new part of the page — just a data attribute.

## The takeover mode

This is the one I'm most pleased with. `data-cursor="takeover"` doesn't just resize the ring — it **becomes the element**:

```html
<button data-cursor="takeover">Get started</button>
```

On hover, the ring springs its width, height, and position to match the target's exact bounding box, copies its computed `border-radius` so a pill button gets a pill cursor and a rounded card gets rounded corners, fills in as a soft highlight, and fades the dot out entirely. Move off, and it springs back into a small circle like nothing happened.

```ts
const enterTakeover = (el: HTMLElement) => {
  const rect = el.getBoundingClientRect();
  ring.style.borderRadius = getComputedStyle(el).borderRadius;
  animate(ringW, rect.width, SIZE_SPRING);
  animate(ringH, rect.height, SIZE_SPRING);
  // ...center it, fade the dot, fill the background
};
```

The trickiest part wasn't the shape-matching — it was keeping that shape locked to the element correctly while the _page_ moves under a stationary mouse, which brings me to the actual hardest bug in the whole build.

## The Lenis trap

Smooth-scroll libraries like Lenis often work by transforming a wrapper `div` instead of using native scroll. That's invisible to almost everything on the page — except `position: fixed`. A CSS `transform` on _any_ ancestor makes that ancestor the containing block for fixed descendants, per spec. Put the cursor inside that wrapper and it quietly stops tracking the viewport, drifting out of sync the moment someone scrolls.

The fix was structural, not clever:

```tsx
<ThemeProvider>
  <Cursor />
  <LenisProvider>{children}</LenisProvider>
</ThemeProvider>
```

`Cursor` lives as a sibling to the scroll wrapper, never inside it. And because Lenis can scroll content under a mouse that hasn't physically moved, I added a scroll-driven recheck so hover state — and the takeover rect — never goes stale between mouse movements.

## What it adds up to

- A **dot + ring** pair with independently tuned spring physics
- **Five hover variants** — default, pointer, text, blend, hidden — all driven by markup
- **Magnetic pull** toward buttons that opt in
- **Takeover mode** that morphs the cursor into the exact shape of whatever it's hovering
- **Touch and reduced-motion aware** — it gets out of the way entirely where it doesn't belong
- Zero layout-thrashing hover checks, even on a Lenis-smoothed, constantly-scrolling page

None of this is flashy in a single screenshot. It's the kind of thing you only notice once it's _not_ there anymore — hover a button below and see for yourself.
